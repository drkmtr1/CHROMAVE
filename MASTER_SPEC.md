# Application Development — Working Specification

## 1. Purpose

Support reliable application delivery with less repeated reading, fewer unnecessary handoffs, recoverable progress, and no silently lost findings. Keep the process lean and adapt it to the actual product, risks, and team. This specification does not prescribe an application stack or architecture.

The Product Owner supplies the product goals and decides scope and acceptance. A copied template is only a starting point: it creates no active task, approval, or release.

## 2. Records and ownership

Keep one authoritative home for each kind of state:

| Record | Owns |
| --- | --- |
| `AGENTS.md` | Short entrypoint and reading route |
| `MASTER_SPEC.md` | Product requirements and governing workflow |
| `PROJECT_STATE.md` | Current baseline, active task/assignments, result, and next authorized action |
| `TODO.md` | All actionable findings and follow-ups in one continuous ledger |
| `DECISIONS.md` | Actual decisions, authorization provenance, scope, and rationale |
| `records/` | Task contracts, results, evidence, and handoffs created when needed |

Start from `AGENTS.md` and current state. Read the active task and its explicit evidence set, plus only relevant findings and specification sections. Expand reads for a stated dependency or uncertainty; do not replay all history by default. The coordinator reconciles shared state and finding records. Agents return evidence and proposed updates.

## 3. Roles and authority

- **Product Owner:** supplies goals and application definitions; owns priorities, consequential product/scope and material architecture/security/dependency/permission/shared-contract choices, bounded planning and implementation authorization, milestone acceptance, and release/publication or template-promotion permission.
- **Codex coordinator:** owns repository routing and truth, routine authorized execution, the smallest useful set of contributors, integration/checks, review coordination, evidence, shared-record reconciliation, and checkpoints; presents bounded decision or lane gates only when needed.
- **Planning & Readiness:** an on-demand in-Codex function for substantive adaptation, requirements/uncertainty/tradeoff analysis, architecture/risk/acceptance/milestone recommendations, material-change planning, product-alignment readiness after technical review, and release or reusable-process advice. It cannot make Product Owner decisions, authorize implementation, accept a milestone, release/publish, substitute for technical review, or implement corrections to a candidate it assesses for readiness.
- **Execution contributors:** implement, test, or supply useful bounded specialist evidence within explicit ownership and authority; no permanent team is required.
- **Technical reviewer:** distinct from the candidate's author and Planning & Readiness; assesses correctness, tests, integration, maintainability, and relevant technical/security/data risks. It reports findings without authoring the reviewed candidate, authorizing implementation, or accepting a milestone.
- **External ChatGPT:** optional independent advice, an explicitly authorized fallback when suitable in-Codex capability or required separation is unavailable, or a deliberate Product Owner escalation for consequential ambiguity. It is not a mandatory normal-cycle handoff. No role claims to have inspected or run what it could not access.

Route substantive planning to an explicitly authorized bounded Planning & Readiness assignment. Save relevant evidence/options and recommendations separately from actual Product Owner decisions. The Product Owner explicitly authorizes the bounded implementation task before dependent execution. An approval to implement does not imply acceptance or publication. Pause only affected dependent work when an unresolved choice would materially change requirements, architecture, safety, scope, or authorization; unrelated already-authorized work may continue.

Use provider/model-neutral logical lanes. Route to **PLANNING_READINESS** for initial application-definition adaptation, an unresolved substantive requirement, consequential architecture/security/dependency/permissions/shared-contract choice, material scope/milestone change, a blocker requiring a different plan, milestone readiness after technical review, final release readiness, or reusable template/process planning. Keep authorized implementation/documentation, routine prechecks/sequencing, tests, ordinary in-scope fixes/reruns, integration, technical-review coordination, finding updates, record reconciliation, and safe checkpoints in **EXECUTION**. A routine failed test or ordinary defect does not require replanning unless its correction changes the authorized contract. Planning advice creates no implementation authority.

A manual lane-transition gate is required only when substantive work warrants a different reasoning capability **and** the exposed client requires user action to obtain it. If the current capability or supported dispatch is suitable, create no manual gate. Do not hard-code a model, provider, effort, hierarchy, or price. When needed, use a compact task-local gate stating ID/state, reason, requested logical lane, exact resumed assignment/candidate, safely known recommendation or UNKNOWN, exact authority granted by continuation, explicit exclusions, and required Product Owner action. A generic `continue` authorizes only the displayed bounded gate work; it grants no material decision, unlisted implementation, acceptance, release, scope expansion, or successor task.

## 4. Delivery and improvement loops

**Application delivery:** define/research the user outcome → record approved requirements and acceptance evidence → implement a bounded task → check and review → integrate only with authorization → reconcile current state.

**Process improvement:** use concrete friction or evidence to propose the smallest useful adjustment, including no change → obtain substantive planning and Product Owner authorization → exercise the candidate → review results → retain, revise, or revert within scope. Do not add process experiments speculatively or build a separate improvement subsystem without demonstrated need and explicit approval.

Use product outcomes, not document or code counts, as milestones. Scale research and architecture to uncertainty. Avoid infrastructure and dependencies for imagined future needs. Keep the instructions adaptable to project size, risks, tools, and stack.

## 5. On-demand contributors

Use one coordinator and the smallest useful set of real contributors. A separate implementer, tester, reviewer, or specialist is useful only when the work or risk warrants it. No permanent roster or fixed number of milestones is required. Assign bounded scope, read/write ownership, evidence, and a stop condition. Do not delegate recursively without explicit authorization. A reviewer reports findings and does not author the candidate under review.

Before relying on delegated or concurrent work, verify the available native tools, permissions, and relevant workspace/isolation capability; record uncertainty rather than inventing a model, configuration, or technical enforcement. Concurrent source writers require verified separate workspaces/worktrees or equivalent isolation, explicit file/interface ownership, and controlled integration. Different branches in one working directory do not establish isolation. Keep one writer for shared state, TODOs, decisions, and common contracts. Use serial execution within the authorized scope when safe concurrency is not established.

Account for every required assignment as completed with evidence or explicitly blocked, failed, canceled, or reassigned. Missing, interrupted, stale, or unverifiable output is not PASS. Preserve available partial work and inspect current ownership and ongoing activity before a replacement proceeds. Do not leave an agent writing after reporting task completion. Check the combined candidate after integration.

Planning & Readiness is an on-demand function, not another permanent manager. Planning may draft only in explicitly owned safe paths; normally it returns evidence/recommendations to the coordinator, who remains the shared-record writer. Readiness uses a fresh non-authoring/read-only assignment relative to the implementation candidate where supported, distinct from its technical reviewer. Non-authoring does not prove hidden-context absence or technical isolation. Record unavailable required separation honestly and use only an explicitly authorized fallback; do not silently claim independent readiness.

## 6. Milestone review and findings

Every milestone receives a full review appropriate to its scope: assess whether the work is correct and advances the product goal. Review the actual identifiable candidate and relevant interactions against requirements, authorization, risks, checks, and unresolved findings. A completion summary alone is insufficient. For documents, review authority, routing, recovery, contradictions, portability, completeness, and workflow behavior; mark runtime checks not applicable when no runtime is involved. Report only checks actually performed.

At each milestone, use a fresh non-authoring technical review agent where supported, alongside self-checks and relevant QA. After technical review and correction evidence, obtain a fresh non-authoring/read-only in-Codex Planning & Readiness assessment where supported under section 5, then stop for the Product Owner's milestone decision. Readiness assesses the identifiable actual candidate, requirements, evidence, findings, risks, and product alignment, returning PASS / REVISE / BLOCKED advice. External ChatGPT remains optional independent advice, an authorized fallback, or a deliberately requested escalation. Routine small approved implementation work may remain lead-only. If a required reviewer, suitable capability, separation, or evidence is unavailable, record the gap and use only a fallback explicitly authorized for that task; do not label self-review as independent review/readiness or missing evidence as PASS. Risk-appropriate affected-scope follow-up may reuse the existing reviewer; a separate reviewer is not required for every command or clerical edit.

### Material contribution verification and correction

Every material contributor output that becomes part of a milestone candidate or its acceptance evidence must receive applicable verification before Product Owner acceptance. This includes coordinator outputs. An output is material when the candidate or acceptance judgment relies on it and an error could meaningfully affect mandatory criteria, product behavior, interfaces/integration, data integrity, safety/security/privacy, user flows, operational readiness, or the validity of acceptance evidence. Individual commands, saves, clerical updates, test invocations and trivial mechanical corrections do not each require a reviewer assignment; a change to their substantive meaning may be material.

The coordinator identifies material outputs, applicable verification responsibilities and evidence in existing task/review records according to the actual work and milestone risks. Verification may include tests/integration checks, technical review, QA/test-design, security/privacy, UX/accessibility, data/integration, domain validation or release/operations verification where relevant. Related outputs may share checks or review; no permanent specialist roster, fixed matrix or reviewer for each contributor is required. Justify omitted or inapplicable dimensions. Missing mandatory verification is not PASS. Architecture/requirements proposals use substantive Planning & Readiness and actual Product Owner decision before dependent work.

Reviewers report findings; the coordinator records them in the single TODO and routes correction to the appropriate authorized contributor/component owner, who need not be the original contributor. Reviewers remain non-authoring for the candidate they review. Correct within the approved contract, run affected checks, and obtain proportionate re-verification. Affected-scope follow-up may reuse the reviewer when effects are bounded and previous evidence remains applicable; broaden technical review when changed behavior, interfaces, shared contracts, dependencies, security/data properties, cumulative interactions or test assumptions extend beyond prior coverage, or bounded follow-up cannot establish mandatory criteria.

Repeat correction and re-verification only while the defect remains correctable within the approved contract. PASS advances toward integration/readiness and the separate Product Owner decision. BLOCKED preserves the prerequisite, findings and available evidence, stops affected dependent work, and exits the correction/re-verification loop to Planning & Readiness/Product Owner decision. State the smallest unblocking action; obtain the required actual Product Owner decision or authorization before affected dependent work resumes. A correction that would materially change requirements, architecture, security, dependencies, permissions, shared contracts, scope, milestone intent or acceptance criteria exits this loop to authorized substantive Planning & Readiness and actual Product Owner decision before dependent execution. Do not continue merely until PASS, weaken criteria/checks, suppress findings, or call missing evidence PASS.

Contribution verification supplements the existing full technical review of the actual combined milestone candidate and relevant interactions; it does not replace it, the distinct fresh non-authoring/read-only readiness assessment where supported or explicitly authorized fallback, or Product Owner acceptance. Retain the smallest useful team, authorized ownership, one shared-record writer unless verified isolation/ownership permits otherwise, assignment accounting, failed attempts and limitations.

Use outcomes with explicit ownership: PASS means applicable mandatory criteria are evidenced; REVISE means an evidenced defect or unmet criterion needs correction; BLOCKED means a prerequisite prevents a valid assessment. Technical PASS and readiness PASS are advisory, not Product Owner acceptance or release permission. Preserve limitations and dissent.

Record every material, minor, disputed, or deferred finding in `TODO.md`, the single finding system. Give each stable identity, source/evidence, affected scope, severity/priority as useful, owner/next action, status, verification criteria, and closure evidence. Do not silently delete or duplicate findings. A deferred item remains unresolved until its revisit or closure conditions are met. Close only after the stated verification is evidenced.

For relevant findings, maintain a concise trace during normal development: issue → impact → corrective action → implementation state → verification → observed outcome → qualified lesson or remaining limitation. Use the original stable finding ID, relevant template/application version context where useful, and links to existing evidence. Distinguish proposed, implemented, and verified-effective actions; use UNKNOWN for unsupported cause/effect or results. Record known or suspected causes with their evidence and uncertainty, and enough application context to explain why an effective action worked and what remains unestablished. Preserve failed attempts, regressions, disputed/deferred items and cases without a verified solution; do not manufacture successful outcomes. At milestone review, check the relevant action/outcome/lesson fields are current within the existing findings review. This uses the same ledger: no separate mandatory lesson file, copied diary or additional approval round for routine logging.

A user-selected derived feedback summary may be manually returned to the explicitly approved Planning & Readiness/Application Building Template planning context, with external ChatGPT as optional advice or authorized fallback. Reference original finding IDs/evidence and relevant version/environment limits; exclude secrets and unrelated or unapproved data. Classify each lesson as application-specific, existing template control / execution discipline, potentially reusable, or insufficient evidence. Preserve the application's authoritative status and provenance; a summary is not another ledger. Feedback/classification authorizes no template change. Any reusable change still follows approved Planning & Readiness planning → Product Owner authorization → Codex implementation/checks and appropriate independent technical review → fresh non-authoring Planning & Readiness assessment where supported or authorized fallback → Product Owner disposition. No automatic cross-project scanner/transfer, telemetry or self-modification authority is implied.

When mutable coordination records could change during or after substantive review, preserve the candidate and relevant evidence on a stable task-owned review surface when useful. Choose the lightest sufficient form; a packet is not required for every trivial review. After substantive review, purely mechanical live-state/status-pointer reconciliation does not require another review unless it changes requirement meaning, authorization, finding substance/disposition, review conclusion, candidate content, or task scope.

When verification could encounter protected, evaluator-only, secret, unrelated, or otherwise prohibited material, declare exact paths and permitted operations before checking. Use targeted checks; avoid broad recursive reads/diffs that could cross the authorized evidence boundary.

## 7. Safety, portability, and readiness

Preserve existing work. Do not reset, clean, overwrite unrelated files, expose secrets, or change external systems without explicit authority. Use only evidence needed for the task. Follow local project permissions and applicable higher-level instructions.

At a meaningful checkpoint, finish the substantive work, reconcile every tracked record, state pointer, decision, and finding intended for that checkpoint, and confirm that no further tracked mutation is planned. Then create the coherent checkpoint commit. When project policy provides an approved private or off-device Git remote and a normal push is safe, push the checkpoint and, only after the last tracked mutation, verify that local `HEAD`, its tracking ref, and the live remote tip agree before claiming final remote equality or a complete remote checkpoint. Any later tracked mutation invalidates that final-equality verification and requires another checkpoint, applicable push, and equality check before final equality may be claimed. If no such remote exists or policy does not require one, do not invent or require it; preserve the local checkpoint and state the limitation. Live Git refs own current revision identity: historical evidence may retain an earlier equality observation, but current coordination must not present that earlier revision as the current tip after later commits, and no tracked record must embed the SHA of the commit that contains that same record.

Do not claim a reusable release from a successful extraction alone. Evaluate the actual clean export, project startup, applicable task/recovery routes, review/finding continuity, product fit, risks, and limitations. State what was not tested; make no unsupported productivity or general-reliability claims. A new project begins with no inherited active task, findings, decisions, authorization, or acceptance.

## 8. Identified export and controlled adaptation

Identify the selected template version/status and reproducible source identity for every reusable export. Default to the latest accepted reusable release when one exists; an evaluation Candidate must be deliberately selected and labeled as such. Do not silently export arbitrary working edits. Follow section 7's source-identity and containing-commit SHA limits.

Markdown is the primary source/export format. Produce one self-contained export faithfully preserving the selected reusable instructions and section 2's operational file boundaries, including authority, review, finding continuity, recovery/checkpoint rules and safety limits. Packaging or another format is a derived view of that source, not an independently maintained master. Exclude template-development and application history, inherited tasks/assignments, findings, decisions/approvals and project acceptance/release state, local identities/paths, secrets and evaluator material. A new application establishes its own baseline, state, findings, decisions, permissions and authority; copying or adaptation creates none of these approvals.

Use a separately supplied application-definition document as the source of product intent. Keep USER REQUIREMENTS distinct from recommendations, assumptions, unresolved questions and actual Product Owner decisions/approvals; never silently promote recommendations to requirements. An explicitly authorized bounded in-Codex Planning & Readiness assignment normally performs adaptation, with external ChatGPT as optional independent advice, authorized fallback, or deliberately requested escalation. Adaptation may propose application-specific requirements, architecture/tradeoffs, milestones, acceptance criteria, test approach, agent/contributor use and Codex-ready initial project records/setup. Preserve the template's controls, including section 6's ongoing finding/outcome/lesson and manual feedback guidance. Generated planning does not authorize implementation; record explicit Product Owner authorization before dependent execution under section 3. Do not automatically update existing applications or transfer data between projects.

### Compact adaptation instruction

> In an explicitly authorized bounded in-Codex Planning & Readiness assignment, use the identified template/export and the separately supplied application-definition document to propose an application plan and initial project records/setup; external ChatGPT is optional advice or authorized fallback. Treat that document as product intent; distinguish USER REQUIREMENTS, recommendations, assumptions, unresolved questions and actual Product Owner approvals. Preserve the selected workflow and operational file boundaries, review/finding/outcome/feedback, recovery and safety controls. Propose requirements, architecture/tradeoffs, milestones, acceptance/tests and contributors appropriate to the product, without assuming a stack or provider. Start with clean project state and its own findings, decisions, permissions and authority. Return the bounded proposal and decisions needed for Product Owner authorization; do not infer implementation or release permission or execute application work.

Instruction implementation/review alone does not establish these capabilities end to end. Keep remaining verification visible: a faithful clean export of the identified source, adaptation against a separate application definition, a fresh-project exercise, and a demonstrated issue/action/verification/outcome/qualified-lesson trace with user-selected manual feedback. Preserve existing verification criteria until that evidence is supplied; documentation PASS is not capability closure or reusable-release acceptance.
